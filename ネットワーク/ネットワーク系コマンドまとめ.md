# ネットワーク系・覚えておくと良いコマンド

> [!summary] このノートの目的
> Linuxを中心に、業務系ITエンジニアがネットワークの状態確認・障害調査・トラブルシュートで使うコマンドを整理する。
>
> 単なるコマンド暗記ではなく、
>
> **「何を確認したいのか → どのコマンドを使うのか → 結果をどう解釈するのか」**
>
> を意識する。

---

## 1. まず覚えたいコマンド

最初から全部覚える必要はない。

まずは以下を「見たことがある」状態にする。

| コマンド                       | 主な用途            | 優先度 |
| -------------------------- | --------------- | --: |
| `ip addr`                  | IPアドレス・NIC確認    | ★★★ |
| `ip route`                 | ルーティング確認        | ★★★ |
| `ping`                     | ICMP疎通確認        | ★★★ |
| `traceroute` / `tracepath` | 通信経路確認          | ★★★ |
| `ss`                       | TCP/UDP・待受ポート確認 | ★★★ |
| `dig`                      | DNS名前解決確認       | ★★★ |
| `curl`                     | HTTP/HTTPS通信確認  | ★★★ |
| `ip neigh`                 | ARP/Neighbor確認  | ★★☆ |
| `tcpdump`                  | パケットキャプチャ       | ★★★ |

| `hostname`                 | ホスト名確認          | ★☆☆ |
| `resolvectl`               | DNS設定・状態確認      | ★★☆ |

# 2. ネットワーク調査の基本的な考え方

ネットワーク障害では、いきなり「アプリが悪い」と考えない。

基本的には下位レイヤから順番に確認する。

```text
アプリケーション
      ↓
HTTP / HTTPS
      ↓
TCP / UDP
      ↓
IP
      ↓
ルーティング
      ↓
NIC / Ethernet
      ↓
物理ネットワーク
```

例えば、

```text
「Webサーバーに接続できない」
```

という問題があった場合、

```text
① NICは正常か？
② IPアドレスは正しいか？
③ デフォルトゲートウェイは正しいか？
④ 宛先までの経路は存在するか？
⑤ 相手ホストまでIP疎通できるか？
⑥ TCP/443などのポートに接続できるか？
⑦ DNSは正しく名前解決できるか？
⑧ HTTP/HTTPSとして正常に応答するか？
```

という順番で切り分ける。

> [!tip] 重要
> 「通信できない」という現象だけでは原因は分からない。
>
> **どの層まで正常なのかを切り分けることがネットワーク調査の基本。**

# 3. IPアドレス・NICを確認する

## 3.1 `ip addr`

IPアドレスやネットワークインターフェースの状態を確認する。

```bash
ip addr
```

短縮形：

```bash
ip a
```

特定のインターフェースだけ：

```bash
ip addr show eth0
```

### 確認できるもの

* NIC名
* MACアドレス
* IPv4アドレス
* IPv6アドレス
* サブネットプレフィックス
* インターフェースのUP/DOWN状態

例：

```text
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP>
    inet 192.168.1.10/24
```

この場合、

```text
IPアドレス : 192.168.1.10
プレフィックス長 : /24
```

つまり一般的には、

```text
ネットワーク : 192.168.1.0/24
```

と考える。

### よくある確認

```bash
ip a
```

↓

```text
「そもそもIPアドレスが付いているか？」
```

を確認する。

---

## 3.2 `ip link`

インターフェース自体の状態を確認する。

```bash
ip link
```

例えば、

```text
eth0: <BROADCAST,MULTICAST,UP,LOWER_UP>
```

などを見る。

### `UP` と `LOWER_UP`

ざっくり、

* `UP` → 管理上有効
* `LOWER_UP` → 下位レイヤのリンクも有効

と考える。

---

## 3.3 `ip -br addr`

一覧を簡潔に表示したい場合に便利。

```bash
ip -br addr
```

例：

```text
lo       UNKNOWN        127.0.0.1/8
eth0     UP             192.168.1.10/24
```

障害調査では、通常の `ip addr` よりこちらのほうが見やすいことも多い。

---

# 4. ルーティングを確認する

## 4.1 `ip route`

ルーティングテーブルを確認する。

```bash
ip route
```

例：

```text
default via 192.168.1.1 dev eth0
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.10
```

意味：

```text
default
  → どの経路にも該当しない通信

via 192.168.1.1
  → デフォルトゲートウェイ

dev eth0
  → eth0から送信
```

### 特に重要

```bash
ip route
```

を実行して、

```text
default via xxx.xxx.xxx.xxx
```

が存在するか確認する。

これがないと、ローカルネットワーク外への通信ができない場合がある。

---

## 4.2 宛先に対してどの経路を使うか確認

非常に便利。

```bash
ip route get 8.8.8.8
```

例えば、

```text
8.8.8.8 via 192.168.1.1 dev eth0 src 192.168.1.10
```

なら、

```text
宛先      : 8.8.8.8
Gateway   : 192.168.1.1
NIC       : eth0
送信元IP  : 192.168.1.10
```

を使うことが分かる。

> [!tip] 実務ポイント
> `ip route` は「ルーティングテーブルを見る」。
>
> `ip route get <宛先>` は「**この宛先へ通信するとき、実際にどう送るかを見る**」。

# 5. 疎通確認

## 5.1 `ping`

最も基本的な疎通確認コマンド。

```bash
ping 192.168.1.1
```

ホスト名でも可能。

```bash
ping example.com
```

回数を指定：

```bash
ping -c 4 192.168.1.1
```

### 確認できること

* ICMPによる疎通
* RTT（往復時間）
* パケットロス

例：

```text
64 bytes from 192.168.1.1: icmp_seq=1 ttl=64 time=0.5 ms
```

見るポイント：

```text
time=0.5 ms
```

→ 往復時間

```text
packet loss
```

→ パケットロス率

---

## 5.2 pingが通らない＝通信できない、ではない

ここは非常に重要。

```text
ping NG
```

だからといって、

```text
TCP通信も必ずNG
```

とは限らない。

理由：

* FirewallがICMPを遮断している
* サーバーがICMP Echoに応答しない
* ネットワーク機器がICMPを制限している

したがって、

```text
ping
↓
TCPポート確認
↓
アプリケーション確認
```

と調査する。

---

# 6. 通信経路を確認する

## 6.1 `traceroute`

宛先までの経路を確認する。

```bash
traceroute 8.8.8.8
```

TCPを使いたい場合：

```bash
traceroute -T -p 443 example.com
```

### 何が分かる？

例えば、

```text
1  192.168.1.1
2  10.0.0.1
3  10.0.1.1
4  ...
```

のように、途中のルーターを確認できる。

---

## 6.2 `tracepath`

Linux環境ではこちらが使える場合もある。

```bash
tracepath 8.8.8.8
```

`traceroute` と同じく経路調査に利用する。

---

> [!warning] `* * *` が出ても即「障害」と判断しない
>
> 途中のルーターがTTL Exceededなどの応答を返さない設定になっている場合がある。
>
> そのため、
>
> ```text
> tracerouteに応答しない
> =
> その地点でパケットが止まっている
> ```
>
> と単純には判断できない。

---

# 7. TCP/UDPポートを確認する

## 7.1 `ss`

Linuxで非常に重要なコマンド。

```bash
ss
```

TCP/UDPのソケット情報を確認する。

よく使う：

```bash
ss -lnt
```

意味：

```text
-l : listening
-n : 名前解決しない
-t : TCP
```

つまり、

> TCPの待受ポート一覧

を確認できる。

---

## 7.2 プロセスも表示する

```bash
sudo ss -lntp
```

例えば、

```text
LISTEN 0 128 0.0.0.0:8080 0.0.0.0:* users:(("java",pid=1234,...))
```

なら、

```text
8080番ポート
↓
Javaプロセス
↓
PID 1234
```

が待ち受けていることが分かる。

### 実務でかなり重要

```text
「サーバーに接続できません」
```

↓

```bash
ss -lntp
```

↓

```text
そもそも対象ポートでプロセスがLISTENしているか？
```

を確認する。

---

## 7.3 TCP接続状態を見る

```bash
ss -ant
```

代表的な状態：

| State        | 意味                         |
| ------------ | -------------------------- |
| `LISTEN`     | 接続待受                       |
| `ESTAB`      | 接続確立                       |
| `TIME-WAIT`  | 接続終了後の待機                   |
| `CLOSE-WAIT` | 相手が切断済み、ローカル側がまだcloseしていない |
| `SYN-SENT`   | SYN送信後、SYN/ACK待ち           |
| `SYN-RECV`   | SYN受信後、ACK待ち               |

> [!tip] 障害調査で重要
> `SYN-SENT` が大量に残っている場合、
>
> **相手からSYN/ACKが返ってきていない**
>
> 可能性などを考える。

---

# 8. TCPポートへの接続確認

## 8.1 `nc`

`netcat`。

TCPポートが接続可能か確認するのに便利。

```bash
nc -vz 192.168.1.20 443
```

意味：

```text
-v : 詳細表示
-z : データを送らずポート確認
```

例えば、

```text
Connection to 192.168.1.20 443 port [tcp/https] succeeded!
```

ならTCP接続自体は成功している。

---

## 8.2 `telnet`

昔から使われる方法。

```bash
telnet 192.168.1.20 8080
```

ただし、現代のLinux環境では`nc`のほうが使いやすいことが多い。

> [!warning]
> `telnet` は「TCP接続できるか」の確認には使えるが、暗号化通信ではない。
>
> HTTPSなどの実通信確認には`curl`を使うほうがよい。

---

# 9. DNSを確認する

## 9.1 `dig`

DNS調査では非常に重要。

```bash
dig example.com
```

特に使う：

```bash
dig example.com A
dig example.com AAAA
dig example.com MX
dig example.com NS
```

### DNSサーバーを指定

```bash
dig @8.8.8.8 example.com
```

これにより、

> 「このDNSサーバーに問い合わせたらどうなるか？」

を直接確認できる。

---

## 9.2 DNS名前解決だけ簡潔に確認

```bash
dig +short example.com
```

例：

```text
93.184.216.34
```

障害調査ではかなり便利。

---

## 9.3 `nslookup`

```bash
nslookup example.com
```

`dig` より簡単に使える。

Windowsでも利用されるため、クロスプラットフォームの知識として覚えておくとよい。

---

## 9.4 `resolvectl`

LinuxのDNS設定・状態確認。

```bash
resolvectl status
```

名前解決：

```bash
resolvectl query example.com
```

systemd-resolvedを利用している環境では特に便利。

---

# 10. HTTP / HTTPSを確認する

## 10.1 `curl`

Web系の障害調査では非常に重要。

```bash
curl https://example.com
```

ヘッダーだけ：

```bash
curl -I https://example.com
```

詳細表示：

```bash
curl -v https://example.com
```

### `curl -v` で確認できること

```text
DNS名前解決
↓
TCP接続
↓
TLSハンドシェイク
↓
HTTPリクエスト
↓
HTTPレスポンス
```

をまとめて観察できる。

---

## 10.2 HTTPステータスコードだけ確認

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://example.com
```

例えば、

```text
200
```

ならHTTPレスポンスとして成功。

---

## 10.3 名前解決を無視して接続先を指定

障害調査で便利。

```bash
curl --resolve example.com:443:192.168.1.20 https://example.com/
```

これにより、

```text
example.com
↓
192.168.1.20
```

として接続できる。

DNSは正常でないが、特定IPのWebサーバーを直接確認したい場合などに使える。

---

# 11. ARP / Neighborを確認する

## 11.1 `ip neigh`

ARPテーブル相当の情報を確認する。

```bash
ip neigh
```

例：

```text
192.168.1.1 dev eth0 lladdr aa:bb:cc:dd:ee:ff REACHABLE
```

意味：

```text
IPアドレス
↓
MACアドレス
```

の対応を確認できる。

### 状態

代表例：

* `REACHABLE`
* `STALE`
* `DELAY`
* `PROBE`
* `FAILED`

---

## 11.2 何に使う？

例えば、

```text
同一LAN内のサーバーに通信できない
```

という場合、

```bash
ip neigh
```

で相手のMACアドレスを解決できているか確認する。

---

# 12. パケットキャプチャ

## 12.1 `tcpdump`

ネットワーク調査で非常に強力。

```bash
sudo tcpdump -i eth0
```

特定ホスト：

```bash
sudo tcpdump -i eth0 host 192.168.1.20
```

特定ポート：

```bash
sudo tcpdump -i eth0 port 443
```

TCPだけ：

```bash
sudo tcpdump -i eth0 tcp
```

---

## 12.2 ICMPを見る

```bash
sudo tcpdump -i eth0 icmp
```

例えば、

```bash
ping 192.168.1.20
```

を実行しながら、

```bash
tcpdump
```

を見る。

すると、

```text
ICMP Echo Request
↓
ICMP Echo Reply
```

が実際に流れているか確認できる。

---

## 12.3 TCP SYNを見る

```bash
sudo tcpdump -i eth0 'tcp[tcpflags] & tcp-syn != 0'
```

TCP接続では、

```text
Client → SYN → Server
Client ← SYN/ACK ← Server
Client → ACK → Server
```

という3-way handshakeが行われる。

tcpdumpでは、このやり取りを直接確認できる。

---

> [!tip] tcpdumpを覚える意味
> `ping` や `curl` は「結果」を教えてくれる。
>
> `tcpdump` は、
>
> **「実際にネットワーク上で何が起きているか」**
>
> を見るための道具。
>
> 原因不明のネットワーク障害を深掘りするときに非常に強力。

---

# 13. NICの統計情報を見る

## 13.1 `ip -s link`

NICの統計情報を確認。

```bash
ip -s link
```

確認できるもの：

* RX packets
* TX packets
* RX errors
* TX errors
* dropped packets

例えば、

```text
RX:
    errors
    dropped
```

などが増えている場合、NICやネットワーク周辺に問題がないか調査する。

---

# 14. `ethtool`

NICの詳細情報を確認する。

```bash
sudo ethtool eth0
```

確認できるもの：

* Link detected
* Speed
* Duplex
* Auto-negotiation

例：

```text
Speed: 1000Mb/s
Duplex: Full
Link detected: yes
```

### インターフェースの統計

```bash
sudo ethtool -S eth0
```

NICドライバ・ハードウェア寄りの詳細な統計情報を確認できる。

> [!note]
> `ethtool` は通常のアプリケーション障害では出番が少ないが、
> **「ネットワークインターフェースそのものがおかしい？」**
> という場合に強い。

---

# 15. ホスト名・名前解決設定

## 15.1 `hostname`

```bash
hostname
```

FQDNなど：

```bash
hostname -f
```

---

## 15.2 `/etc/hosts`

ローカル名前解決を確認。

```bash
cat /etc/hosts
```

例えば、

```text
192.168.1.20 app-server
```

と記載されていれば、

```text
app-server
↓
192.168.1.20
```

として名前解決される場合がある。

---

## 15.3 `/etc/resolv.conf`

DNS設定を確認。

```bash
cat /etc/resolv.conf
```

例えば、

```text
nameserver 192.168.1.1
```

など。

> [!warning]
> `/etc/resolv.conf` は環境によってNetworkManagerやsystemd-resolvedなどによって自動生成される場合がある。
>
> 「このファイルを直接編集すればOK」とは限らない。

# 18. トラブルシュート実践例

## ケース1：サーバーから外部サイトに接続できない

例えば、

```text
サーバーから https://example.com にアクセスできない
```

### Step 1：IPアドレス

```bash
ip addr
```

確認：

```text
IPアドレスが付いているか？
NICがUPか？
```

---

### Step 2：ルーティング

```bash
ip route
```

確認：

```text
default routeがあるか？
```

---

### Step 3：Gatewayへの疎通

```bash
ping -c 4 <default-gateway>
```

NGなら、

```text
NIC
IP設定
VLAN
ARP
Gateway
```

などを疑う。

---

### Step 4：外部IPへの疎通

```bash
ping -c 4 8.8.8.8
```

ここまで通れば、

```text
IPレベルの外部通信
```

はできている可能性が高い。

---

### Step 5：DNS

```bash
dig example.com
```

名前解決できるか確認。

---

### Step 6：HTTPS

```bash
curl -v https://example.com
```

ここで、

```text
DNS
TCP
TLS
HTTP
```

のどこで失敗しているかを調べる。

---

### Step 7：必要ならtcpdump

```bash
sudo tcpdump -i eth0 host <宛先IP>
```

実際にパケットが送受信されているか確認。

---

# 19. トラブルシュート実践例：Webサーバーに接続できない

```text
Client
  ↓
Web Server
```

Webサーバー：

```text
192.168.1.20:443
```

### ① IP疎通

```bash
ping -c 4 192.168.1.20
```

---

### ② TCPポート

```bash
nc -vz 192.168.1.20 443
```

## 20. 「どこまで通っているか」を考える

ネットワーク障害では、以下のように段階的に考える。

```text
① NIC
 ↓
② IP
 ↓
③ Gateway
 ↓
④ Routing
 ↓
⑤ ICMP
 ↓
⑥ TCP
 ↓
⑦ TLS
 ↓
⑧ HTTP
 ↓
⑨ アプリケーション
```

例えば、

```text
ping OK
nc -vz 443 NG
```

なら、

```text
IPレベル     → OK
TCP 443      → NG
```

なので、

```text
Firewall
WebサーバーのLISTEN
Load Balancer
Security Group
ACL
```

などを調査する。

一方、

```text
nc OK
curl NG
```

なら、

```text
TCP接続       → OK
HTTP/HTTPS    → NG
```

なので、

```text
TLS証明書
HTTP設定
Webサーバー
リバースプロキシ
アプリケーション
```

などを疑う。

# 21. TCP 3-way handshakeを理解する

TCP通信を調査するなら、これは覚えておきたい。

```text
Client                     Server

  | ------ SYN ----------> |
  | <----- SYN/ACK ------- |
  | ------ ACK ----------> |
  |                         |
  | ===== TCP通信 =======> |
```

これを、

```text
SYN
↓
SYN/ACK
↓
ACK
```

と覚える。

---

## tcpdumpで見る

```bash
sudo tcpdump -i eth0 host 192.168.1.20 and port 443
```

### パターンA：SYN → SYN/ACK → ACK

```text
Client → SYN → Server
Client ← SYN/ACK ← Server
Client → ACK → Server
```

→ TCP接続成功。

---

### パターンB：SYN → SYN → SYN...

```text
Client → SYN → Server
Client → SYN → Server
Client → SYN → Server
```

→ SYN/ACKが返ってこない。

例えば、

* Firewall
* 経路
* 相手ホスト停止
* パケット破棄

などを疑う。

---

### パターンC：SYN → RST

```text
Client → SYN → Server
Client ← RST ← Server
```

→ TCP接続を拒否された可能性。

例えば、

```text
対象ポートでLISTENしていない
```

などを考える。

| ------------ | ------------ | ---------------- |

# 28. 実務での基本フロー

「通信できない」と言われたら、以下を意識する。

```text
┌─────────────────────────┐
│ ① IP / NIC              │
│    ip addr               │
│    ip link               │
└────────────┬────────────┘
             ↓
┌─────────────────────────┐
│ ② Routing               │
│    ip route              │
│    ip route get          │
└────────────┬────────────┘
             ↓
┌─────────────────────────┐
│ ③ IP疎通                │
│    ping                  │
└────────────┬────────────┘
             ↓
┌─────────────────────────┐
│ ④ TCP/UDP               │
│    nc                    │
│    ss                    │
└────────────┬────────────┘
             ↓
┌─────────────────────────┐
│ ⑤ DNS                   │
│    dig                   │

└────────────┬────────────┘
             ↓
┌─────────────────────────┐
```

> **「通信できない」ではなく、「どの段階まで通信できているのか？」に分解する。**

# 31. 最終的なゴール

コマンドを100個暗記することが目的ではない。

最終的には、

```text
「サーバーAからサーバーBの443番ポートに接続できない」
```

と言われたときに、

```text
「まずIP設定を見よう」
        ↓
「次に経路」
        ↓
「Gatewayまで届くか」
        ↓
「BまでIP疎通するか」
        ↓
「443/TCPに接続できるか」
        ↓
「Bで443がLISTENしているか」
        ↓
「DNSは関係しているか」
        ↓
「必要ならtcpdumpでパケットを見る」
```

と、**調査の道筋を自然に組み立てられること**を目指す。

> [!quote] 覚え方
> **コマンドを覚えるのではなく、「ネットワークに質問する方法」を覚える。**
>
> `ip addr`
> → 「このマシンはどんなIPを持っている？」
>
> `ip route`
> → 「パケットはどこへ送る？」
>
> `ping`
> → 「相手までIPレベルで届く？」
>
> `nc`
> → 「このTCPポートに接続できる？」
>
> `dig`
> → 「この名前をIPに変換できる？」
>
> `curl`
> → 「Web通信として成立する？」
>
> `tcpdump`
> → 「実際に何がネットワーク上を流れている？」
>
> この感覚が身につけば、ネットワーク障害に遭遇したときの切り分け能力が大きく上がる。
