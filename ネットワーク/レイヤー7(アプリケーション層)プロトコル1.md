# HTTP

## HTTPのメッセージフォーマット

HTTPでやりとりする情報を**HTTPメッセージ**という。

HTTPメッセージには以下の2種類がある。

* **リクエストメッセージ**：クライアント → サーバー
* **レスポンスメッセージ**：サーバー → クライアント

HTTPメッセージは、概念的に以下で構成される。

* **制御データ**：メッセージの主目的や概要
* **ヘッダーセクション**：メッセージやコンテンツの付加情報
* **コンテンツ**：アプリケーションデータの本文

### HTTP/1.1のメッセージフォーマット

HTTP/1.1では、**テキスト形式のHTTPメッセージ**をTCPコネクション上でやりとりする。

#### リクエストメッセージ

制御データに**リクエストライン**、ヘッダーセクションに**ヘッダーフィールド**が格納される。

##### リクエストライン

以下の3つで構成される。

* **メソッド**：リクエストの種類
* **リクエスト対象**：リクエストする対象
* **HTTPバージョン**

例：

```text
GET /index.html HTTP/1.1
```

#### レスポンスメッセージ

制御データに**ステータスライン**、ヘッダーセクションに**ヘッダーフィールド**が格納される。

##### ステータスライン

処理結果の概要を返す行。

* **HTTPバージョン**
* **ステータスコード**：処理結果を3桁の数字で表す
* **リーズンフレーズ**：ステータスコードの理由

例：

```text
HTTP/1.1 200 OK
```

### HTTP/2のメッセージフォーマット

HTTP/2では、**1本のTCPコネクション内に複数のストリームを作り、バイナリ形式のフレームを多重化して通信する**。

* **ストリーム**：HTTPメッセージを論理的に分離する仮想的な通路
* **フレーム**：HTTP/2で通信する最小単位
* **ストリームID**：フレームが属するストリームを識別する

主なフレーム：

* **HEADERSフレーム**：ヘッダーセクションなどを格納
* **DATAフレーム**：コンテンツを格納

HTTP/1.1のリクエストライン・ステータスラインに相当する情報は、HTTP/2では**疑似ヘッダーフィールド**として扱われる。

#### HPACK

HTTP/2のヘッダーフィールドを圧縮する仕組み。

* よく使われるヘッダーをあらかじめ定義された番号で表す
* 一度送信したヘッダーを動的テーブルに登録して再利用する

これにより、ヘッダーフィールドの転送量を削減する。

## HTTP/2の接続パターン

HTTP/2では、接続状況に応じて以下のような接続方法がある。

### SSLハンドシェイクパターン

TLSの**ALPN**を利用して、HTTP/2（`h2`）を使用することをネゴシエーションする。

HTTPSでHTTP/2を利用する場合に一般的な方式。

### ヘッダーフィールドパターン

TLSを使用しない場合、HTTP/1.1の**Upgrade**ヘッダーフィールドを利用してHTTP/2への切り替えを要求する。

この方式は**h2c**と呼ばれる。

### ダイレクト接続パターン

サーバーがHTTP/2に対応していることがあらかじめ分かっている場合、最初からHTTP/2で接続する。

### HTTP/3（補足）

HTTP/3は、HTTP/2と同様にストリームによる多重化を行うが、**TCPではなくQUIC上で動作する**。

```text
HTTP/3
 ↓
QUIC
 ↓
UDP
 ↓
IP
```

# SSL/TLS

## SSLが使用している技術

現在はSSLではなく**TLS**が使用されている。

TLSは主に以下の脅威に対抗する。

* **盗聴** → 暗号化
* **改ざん** → MACなどによる完全性検証
* **なりすまし** → デジタル証明書・デジタル署名による認証

## SSLを支える技術

### 暗号化アルゴリズム

TLSでは、実際のアプリケーションデータの暗号化に**共通鍵暗号方式**を使用する。

* **ストリーム暗号方式**：ビットやバイト単位で暗号化
* **ブロック暗号方式**：一定サイズのブロック単位で暗号化

公開鍵暗号方式と比較して高速なため、大量の通信データの暗号化に適している。

### 鍵交換アルゴリズム

通信に使用する共通鍵を安全に確立するため、**DHEやECDHE**などの鍵交換アルゴリズムを使用する。

公開鍵・秘密鍵の仕組みを利用し、秘密そのものを通信相手に送らずに共有秘密を確立する。

### デジタル署名アルゴリズム

デジタル署名を利用して、通信相手が正しい相手であることを確認する。

デジタル署名にはRSA署名やECDSAなどがある。

**秘密鍵で署名し、公開鍵で検証する**。

### 公開鍵暗号方式

暗号化鍵と復号鍵に異なる鍵を使用する方式。

* **公開鍵**：公開してよい
* **秘密鍵**：本人だけが保持する

RSA暗号では、RSA公開鍵とRSA秘密鍵の鍵ペアを使用する。

> TLS 1.2ではRSAは鍵交換にも利用できるが、DHE/ECDHEによる鍵交換も利用される。

### メッセージ認証アルゴリズム

**MAC（Message Authentication Code）**を利用して、通信データが改ざんされていないことを確認する。

TLS 1.2では、暗号方式とMAC方式を組み合わせて通信データを保護する。

#### AEAD

**AEAD（Authenticated Encryption with Associated Data）**は、暗号化と認証を一体化した方式。

TLS 1.2でもAEAD暗号スイートを利用できる。

TLS 1.3ではAEADが標準的に利用される。

## SSLのレコードフォーマット

TLSによって運ばれるデータを**TLSレコード**として扱う。

基本的な構成要素：

* コンテンツタイプ
* プロトコルバージョン
* ペイロード長
* ペイロード

TLSレコード単位でアプリケーションデータなどを分割して送信する。

## SSLの接続から切断までの流れ

### 事前準備フェーズ

サーバー側で秘密鍵を用意し、認証局（CA）から**デジタル証明書**を発行してもらう。

デジタル証明書は、**Webサイトの身元と公開鍵を結び付けるもの**。

### SSLハンドシェイクフェーズ

クライアントとサーバーの間で、

* 使用するTLSのバージョンや暗号方式などを決定
* サーバーを認証
* 鍵交換を実行
* 通信用の鍵を確立

する。

TLS 1.2では、RSAやDHE/ECDHEなどの鍵交換方式を利用できる。

### メッセージ認証・交換フェーズ

ハンドシェイクで確立した鍵を使用して、アプリケーションデータを暗号化・認証して送受信する。

HTTPSでは、この中でHTTPメッセージを安全に通信する。

### クローズフェーズ

TLS通信を終了し、接続を閉じる。

## TLSの全体像

TLSの仕組みは、以下の流れで理解するとよい。

```text
① TLSハンドシェイク
   ├─ 通信条件を決定
   ├─ サーバーを認証
   └─ 鍵交換・通信用の鍵を確立
          ↓
② 暗号化通信
   └─ 共通鍵暗号（MAC / AEAD）でデータを保護
```

**公開鍵暗号・デジタル署名などは認証や鍵交換に利用し、実際の大量の通信データは共通鍵暗号で高速に暗号化する**、という役割分担が重要。

### TLS 1.3（補足）

TLS 1.3ではTLS 1.2から仕組みが整理され、

* RSAによる鍵交換を廃止
* ECDHEなどの方式を使用
* AEADを使用
* ハンドシェイクの往復回数を削減

などの変更が行われている。

```text
HTTPS
 ↓
HTTP
 ↓
TLS
 ↓
TCP
 ↓
IP
```

HTTP/2の場合も基本的な関係は同じで、HTTP/2をTLSで保護してHTTPSとして通信する。
